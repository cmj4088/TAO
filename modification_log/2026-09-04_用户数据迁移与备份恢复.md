### 过程中发现并修复的 Bug
- **gunicorn 4 worker 并发 init_db 竞争**：worker 各自跑 Alembic 迁移在 SQLite 上竞争，全部启动失败（exit 3）→ `database.py` 新增 `_boot_lock()` 跨进程启动锁（fcntl/msvcrt）
- **VACUUM INTO 同秒撞名**：备份文件名只到秒，多 worker 同秒启动时第二个报 "output file already exists" → 文件名追加 `secrets.token_hex(3)` 随机后缀
- 修复后本地 6 线程并发 init_db、副机 4 worker 默认 CMD 冒烟均通过（0 ERROR）

### 改动文件

## 修改内容

### 需求
> "我需要你理解这个项目，并完善用户账户迁移的功能，保证系统后端前端更新时不影响用户使用"

经 grill-me 对齐（4 问）：③ schema 自动迁移 + 导出/导入都做；机制用市面标准 **Alembic**；备份/恢复用 **SQLite 原生备份**（标准 .db 文件 + 管理 API + 迁移前自动备份滚动保留）；部署者是老师，必须"替换重启"零手动操作。

### 改动说明

**1. schema 迁移机制（Alembic 接管建表）**
- `backend/requirements.txt`：新增 `alembic==1.13.3`
- `backend/alembic.ini`、`backend/alembic/env.py`、`backend/alembic/script.py.mako`：迁移基础设施（ini 保持纯 ASCII，Windows GBK locale 下 configparser 解码 UTF-8 中文注释会崩）
- `backend/alembic/versions/0001_initial.py`：基线版本，覆盖 v2.0.1 全部 8 张表（settings/roles/permissions/role_permissions/users/sessions/user_llm_configs/verify_codes）
- `backend/app/database.py`：
  - 路径改为锚定文件位置的绝对路径（不再受工作目录影响）
  - `init_db` 不再 `Base.metadata.create_all`，改为：迁移前 `VACUUM INTO` 自动备份 → Alembic `upgrade head`（存量库无 `alembic_version` 时先 `stamp 0001_initial` 接管）→ 失败回滚备份并抛错拒绝启动
  - 新增 `_backup_database` / `_run_migrations` / `reload_engine`
- **以后改表结构的流程**：`alembic revision --autogenerate -m "xxx"` → 检查脚本 → 随代码部署，启动时自动升级，老师无感

**2. 备份/恢复 API（backend/app/routers/backup.py 新增）**
- `GET /api/admin/backup/export`（settings:write）：`VACUUM INTO` 导出标准 .db 下载，后台任务清理服务端临时文件
- `POST /api/admin/backup/restore`（settings:write）：integrity_check + 核心表校验 → 自动备份当前库 → **SQLite backup API 整库覆盖**（不用 os.replace 替换文件：请求期间认证依赖还握着 tao.db 连接，Windows 下会 WinError 5）→ 补跑迁移
- `backend/app/main.py`：注册 backup 路由

**3. 前端管理页（frontend/src/pages/AdminPage.tsx）**
- 新增"数据备份与迁移"卡片：导出备份（blob 下载）/ 导入恢复（选文件 → AlertDialog 二次确认 → multipart 上传 → 成功后清 token 跳登录页）
- 导出/上传用裸 axios（通用 client 的 JSON Content-Type 会破坏 multipart boundary；且需要 120s 长超时）
